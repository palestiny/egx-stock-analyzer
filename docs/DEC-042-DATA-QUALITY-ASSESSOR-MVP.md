# DEC-042 — Data Quality Assessor MVP

**Status:** Accepted
**Date:** 2026-09-16

## 1. Design Question

How should M9 turn raw market observations into explicit data-quality assessments without moving validation rules into `PriceBar` or changing the analytical core?

## 2. Decision

Introduce a small `RawPriceBarObservation` model and a deterministic `DataQualityAssessor`.

The assessor evaluates a list of raw observations and returns one immutable `DataQualityAssessment` per observation.

The assessor does not create `PriceBar`, fetch data, persist data, or run analysis.

## 3. Raw Observation Boundary

`RawPriceBarObservation` deliberately permits missing values and an unvalidated timestamp so the quality boundary can observe problems before the stricter `PriceBar` model is constructed.

Fields:

- stock identity
- timeframe
- timestamp
- open
- high
- low
- close
- volume

No provider-specific fields are introduced in this MVP.

## 4. MVP Rules

### Missing Values

Any required observation field that is `None` produces:

```text
MISSING_VALUE
```

and makes the assessment `INVALID`.

### Invalid Values

Negative OHLC prices or negative volume produce:

```text
INVALID_VALUE
```

and make the assessment `INVALID`.

### Timestamp

A timestamp that is naive (not timezone-aware) produces:

```text
INVALID_TIMESTAMP
```

and makes the assessment `INVALID`.

### OHLC Consistency

When all OHLC values are present, the assessor requires:

```text
high >= max(open, close)
high >= low
low <= min(open, close)
```

Violation produces:

```text
OHLC_INCONSISTENCY
```

and makes the assessment `INVALID`.

### Duplicate Observation

Observation identity is:

```text
Stock + Timeframe + Timestamp
```

If that identity occurs more than once in the assessed input, each duplicate receives:

```text
DUPLICATE_OBSERVATION
```

A duplicate-only finding produces `SUSPECT`, not `INVALID`, because the observation may become usable after duplicate reconciliation.

## 5. Status Mapping

The mapping is explicit:

```text
Any INVALID-class issue
        ↓
INVALID

Duplicate only
        ↓
SUSPECT

No issues
        ↓
VALID
```

The `UNKNOWN` status remains part of the domain vocabulary but is not generated by this MVP. Empty input returns an empty result rather than inventing an unknown observation.

If an observation has both duplicate and invalid-value findings, `INVALID` takes precedence while both issues are preserved.

## 6. Boundaries

The assessor does not own:

- provider-specific rules
- trading calendar/session rules
- missing trading-day inference
- corporate-action adjustment
- price correction
- deduplication/reconciliation
- persistence
- analysis
- scoring
- opportunity classification

It reports quality evidence; it does not silently repair observations.

## 7. TDD Acceptance Criteria

1. Valid observation → `VALID` and analysis eligible.
2. Missing required value → `INVALID` + `MISSING_VALUE`.
3. Negative price/volume → `INVALID` + `INVALID_VALUE`.
4. Naive timestamp → `INVALID` + `INVALID_TIMESTAMP`.
5. Inconsistent OHLC → `INVALID` + `OHLC_INCONSISTENCY`.
6. Duplicate identity → `SUSPECT` + `DUPLICATE_OBSERVATION`.
7. Invalid finding takes precedence over duplicate-only status.
8. Empty input produces an empty assessment sequence.
9. Repeated evaluation is deterministic.

## 8. Trade-offs

### Raw Observation instead of `PriceBar`

Allows the quality boundary to detect missing and malformed values before strict domain construction.

Trade-off: introduces a second market-data representation. This is intentional because raw observation and validated domain observation have different responsibilities.

### Duplicate → SUSPECT

Avoids declaring the underlying observation mathematically invalid merely because the input contains a duplicate.

Trade-off: downstream reconciliation is still required before analysis.

### No Missing-Date Detection

The MVP does not infer missing trading sessions because an exchange calendar is not yet modeled.

Trade-off: completeness analysis is deferred rather than guessed.

## 9. Consequence

The operational pipeline can now evolve toward:

```text
Raw Provider Observation
        ↓
DataQualityAssessor
        ↓
DataQualityAssessment
        ↓
Eligible Observation
        ↓
PriceBar / Analysis
```

The next design gate must decide how a `VALID` raw observation becomes a `PriceBar` and how `SUSPECT` observations are reconciled or excluded before analysis.
